# Sensor unit catalog, SensorType and Sensor type suggestions

Where unit knowledge comes from (only the API catalog - no hard-coded unit anywhere, enforced by a test), unit labels on lists and charts, the import's exact-unit validation, the removal of the aggregation type / explanation, the QuantityKind -> SensorType rename and the Data sets workbook, and the Sensor type dropdown.

Related: the API side of this feature is in [../../../PRECOG_API/docs/features/sensor-metadata.md](../../../PRECOG_API/docs/features/sensor-metadata.md).

The text below was moved verbatim from `CLAUDE.md` (Dashboard) on 2026-11-19; dates and "superseded" notes are the original ones. Keep this file up to date with every change to the feature.

## Sensor unit and aggregation metadata

> **Superseded in part:** the aggregation type and explanation described in this section were **removed** from the import, the Policies tab and the API/DB - see "Aggregation type / explanation removed". The unit part (catalog from `GET /api/SensorMetadata`, exact-unit validation of known metrics, unit labels, chart units) stays.


The API owns a catalog of units, aggregation types and the 163 Vibration_Duo metrics (`GET /api/SensorMetadata`, `useSensorMetadata` in `src/api/hooks/sensorMetadata.ts`). **That catalog is the only source of unit/aggregation knowledge in this app.** No file maps a metric name or family to a unit, and none contains a unit code or aggregation type as a string literal - `src/test/noHardcodedMetadata.test.ts` fails if one appears. The aggregation type is metadata only; nothing here aggregates anything.

- **Display**: `SensorDto` carries `unitCode`, `unitLabel`, `unitLabelHu`, `aggregationType`, `aggregationExplanation`. `MetricDefinitionCard` (Sensor Policies page) shows display name, machine name, unit label with its code, aggregation type with its code, and the explanation; a Sensor that is a known metric but lacks the metadata gets a visible error (nothing guessed), an ordinary Sensor a plain notice. The Device detail Sensor row shows `unitLabel`. The general dimension of a metric without one (kurtosis, crest factor) is the unit `one`, labelled **"Unit"** by the API; energy metrics are "Relative spectrum energy" (`raw_energy`).
- **Charts**: `TelemetryChart` takes `unitLabel` per series (from the API) for the y-axis title and the tooltip (`sharedUnitLabel`, `unitLabelOfDataset`). Two different units never share one axis title; a series with no unit gets none.
- **Import** (`src/lib/sensorImport.ts`, `SensorImportDialog`): new columns `sensorName` (the Sensor's `externalSensorId`; the cell holds the full id `{machineName}_{point}`; `machineName` and `externalSensorId` are accepted aliases), `displayName`, `unitCode`, `aggregationType`, `aggregationExplanation`. The catalog is required (no catalog = the import is blocked). A row whose id exactly matches a known metric must carry exactly that metric's unit, type and explanation; any problem is listed by sheet line, field and value and blocks the whole import before the first request. The dialog lists the allowed units and types from the catalog, the preview shows unit, aggregation type, explanation and validation state per row, and the template (built from catalog examples, one per unit/aggregation combination) is generated from the same catalog. Unit, type and explanation are sent unchanged to `POST .../Sensors`.
- **Samples** `samples/vibration-duo-*.csv` carry the metadata of all 163 / 326 rows and are tested against the catalog fixture (`src/test/fixtures/sensorMetadataCatalog.json`, a dump of the endpoint - test data only).
- **No Sensor export exists** in this dashboard.

## "Data sets" workbook and the QuantityKind -> SensorType rename

- **Rename.** The Sensor's former `quantityKind` is now **`sensorType`** everywhere: DB column (`pg.sensors.sensortype`, `pg.deviceknowledgesharesensormaps.normalizedsensortype`), API fields (`SensorDto`/create/update requests `sensorType`, knowledge-sharing `normalizedSensorType`), generated schema, hooks, the "Sensor type" form fields, the import column `sensorType` and all docs. It stays a free-text description of what the Sensor measures (temperature, vibration...); it is part of the knowledge-sharing compatibility proof. The old import headers `quantityKind` / `quantity` are still accepted. **This is a breaking API change**: a client sending `quantityKind` no longer sets it (the Dashboard was updated with the API; the one-off script is `DB_SensorType_Rename.sql` in the API repo - run it before deploying).
- **Data sets workbook.** The import dialog's **Download Data sets** button builds `sensor-import-data-sets.xlsx` in the browser (`src/lib/sensorDataSets.ts`, `src/lib/xlsxWriter.ts` - a small dependency-free writer, no library added): an Overview of every import column (required?, what to enter, where the values are) plus one sheet per selectable field - `direction`, `rawScale`, `processingEnabled` (from the importer's own constants), `unitCode`, `aggregationType` (from the API catalog, with labels, valid units and explanations) and **Known metrics** (all 163 with exact unit/aggregation/explanation). Nothing about units or aggregations is written in this file; tests check the workbook lists exactly what the importer accepts.

## Sensor type dropdown

The "Sensor type" field of the Add/Edit Sensor dialogs (`SensorTypeInput.tsx`, a Fluent `Combobox` in free-text mode) drops down the Sensor types already in use in the Company, from `GET /api/SensorTypes` (`useSensorTypes`, 5 min stale time, invalidated when a Sensor is created, updated or imported). Click an entry to fill the field; typing narrows the list (`filterSensorTypes` in `src/lib/sensorTypes.ts`: case-insensitive "contains"; the whole list again when the value already is one of the types); anything not in the list is simply a new type - the field stays free text, and it is a plain text box if the list cannot be loaded. The list is the API's (Admin: whole Company; Reader: granted Devices) and is never extended or corrected here. The Device page's old line "There is no permanent delete" was replaced, as it was wrong since the Device deletion was added.

Testing: opening a Fluent Combobox popup hangs jsdom (see `MoveToCanonicalDialog.test.tsx`), so the unit tests cover the filter logic and render the field; the dropdown interaction itself was checked in a real Chromium (Playwright, every API request answered by the script - nothing left the machine): click lists all types, picking fills the field, an existing value re-opens the whole list, "PRE" narrows to "pressure", a new value stays as typed, no page errors.

## Aggregation type / explanation removed; import column names

- **Removed**: `aggregationType` / `aggregationExplanation` are no longer in the Sensor import (template, parsing, validation, preview, the request sent to `POST .../Sensors`), the "Data sets" workbook (the `aggregationType` sheet and the two columns of "Known metrics"), the sample CSVs, or the Policies tab's Metric definition card. An old sheet that still has the two columns gets them reported as "ignored column(s)" and nothing is sent. The API and database dropped them too (see the API docs and `DB_SensorAggregationMetadata_Remove.sql`); long-term aggregation is set up per Sensor through the aggregation policies. `src/test/noHardcodedMetadata.test.ts` fails if the names reappear in application code.
- **What stays**: the unit catalog (`useSensorMetadata`: units + 163 known metrics with their unit), exact-unit validation of a known metric, unit labels on the Sensor list and charts, one template example row per catalog unit.
- **Policies tab card**: the label "Machine name" is now **"Sensor name"** (the Sensor's `externalSensorId`); the card shows display name, Sensor name and unit only. The import preview's column is "Sensor name" too.
- **Calculate**: the import column for the per-Sensor calculation switch is now **`Calculate`** (true/false, 1/0, yes/no, on/off, igen/nem; accepted aliases: `processingEnabled`, `Processing`, `Calculation`), the dialog's default field and the preview column are labelled "Calculate", the Data sets sheet is "Calculate", and a bad value is reported on `Calculate`. The API field is still `processingEnabled`.
