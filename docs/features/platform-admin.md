# Own user management: the platform administrator, invitations and password reset

The WordPress-independence work (S1 schema, S2 sign-in from the User store) is described in `company-identity.md`. This file covers S3: the platform account (VSSSysAdmin), creating Companies, the single-use mail links (invitation, password reset) and the rule that a Company keeps an Admin.

## The platform administrator (VSSSysAdmin)

- **One account, configured only by the `.env`**: `PLATFORM_SYSADMIN_EMAIL` and `PLATFORM_SYSADMIN_HASH_B64`. The hash is the base64 of a password hash (WordPress `$wp$` bcrypt or phpass `$P$`) - base64 because the hash contains `$`, which Docker Compose's `env_file` and shells may interpolate (`AccountManagementTests` runs the hash through `DotEnv` and checks it decodes identically). The account is not in the database; a missing, half-given or invalid setting only makes the account unavailable (a warning without any value is written; the application starts). Both values or none.
- **Sign-in**: the normal `POST /api/Authentication/Request_HMAC_Key` with the e-mail address (any case); the platform account is checked FIRST and wins over a same-named User or WordPress account. Same rate limit, throttle and token format as everyone: a failed attempt is counted under the SHA-256 of the name (`loginattempts.identitykey`), delayed from the 6th attempt. The token is recomputed from the hash after a restart (cache id `PlatformAdmin.CacheId`). Rotating the password = a new base64 in the `.env` and a restart.
- **What it may do** (`PlatformController`, `/api/Platform/...`, all `[ValidateHMAC]` + `[AllowPlatformAdmin]`): list Companies (name, state, user / Admin counts), create a Company (unique name, http(s) website), enable / disable one (not a `Locked` one), list the people of a Company, invite a person (the first Admin, or anyone) by e-mail, list / withdraw pending invitations, grant / revoke the Admin or Reader role.
- **What it may NOT do**: everything else. `ValidateHMACAttribute.Finish` is default-deny for `ActorType.PlatformAdmin`, exactly like for a DevicePrincipal: an endpoint without `[AllowPlatformAdmin]` answers it 403, so it never sees telemetry, Issues, Devices or models, and there is no cross-Company browsing of Company data. Only `GET /api/User/GetUserDetails` (with `isPlatformAdmin = true`, no Company) and the Platform endpoints are open to it. The Platform actions also check the actor type, so an ordinary Admin that the filter lets in gets 403.
- **Never inserted by synchronization or invitation**: the platform e-mail cannot be invited (409) and is not a Company member.

## Invitation and password reset (the single-use links)

- **Token**: 32 random bytes (URL-safe base64, 43 characters), only its SHA-256 is stored (`pg.usertokens.tokenhash`), single use (`UserTokenService.ClaimAsync` is one atomic UPDATE), invitation 7 days, reset 1 hour. A new token for the same person and purpose revokes the earlier one. The raw token exists only in the mail; it is never logged, returned by a list, or stored. The link carries it in the URL **fragment** (`.../accept-invite#token=...&lang=hu`), which a browser never sends to a server or proxy.
- **Mail**: `AccountMailer` (English / Hungarian by the token's language) through the same sender and `IssueEmail` settings as the Issue e-mails; the link base is `Dashboard__BaseUrl` (https, or http for localhost). No Dashboard address / mail off / no `IssueEmail__Password` = nothing is sent (the invitation exists, the response says `emailSent: false`), nothing throws, nothing sensitive is logged (only the exception type of a mail-server failure). The password of the sending mailbox now lives only in the `.env` (`IssueEmail__Password`); it was removed from the source on 2026-11-24 and the deploy refuses to run without it.
- **Anonymous endpoints** (`AccountsController`, rate limit policy `AccountToken` 10 / minute; the single-use token is the credential; every unknown / used / expired / revoked token is the same 404): `POST /api/Accounts/Invitations/Info`, `.../Invitations/Accept`, `.../PasswordReset/Request` (always 204, the work is done after the answer so that the time does not tell whether the address exists; only an enabled, locally created User with a password is mailed, at most once a minute; a WordPress / Entra User keeps its password at the source), `.../PasswordReset/Confirm` (sets the new password and drops every cached access key of the account).
- **Accepting** creates the User (login name = e-mail, `source` Local, the invited role, a `$wp$` hash, language from the invitation) and uses the token up in one transaction. 409 if the address already belongs to a User (a person in two Companies is a later slice).
- **Password rules** (`PasswordPolicy`): 10-128 characters, not blank, at least four different characters, not the e-mail address; the reason never echoes the password.

## A Company keeps its Admin

`CompanyAdminGuard`: revoking the Admin role of the Company's last **enabled** Admin is refused with 409 - by the platform administrator (`DELETE .../Members/{userId}/Roles/Admin`) and by the Company's own Admin (`DELETE /api/Company/Members/{userId}/Roles/Admin`). The check and the change run in one transaction under a per-Company advisory lock (`pg_advisory_xact_lock`), so two simultaneous revocations cannot both pass. A `Locked` (WordPress-synchronized) User's roles are not changed here (409). Disabling / deleting a User follows the same rule in the Company-Admin slice (S4).

## Settings (.env, see `.env.example`)

`PLATFORM_SYSADMIN_EMAIL`, `PLATFORM_SYSADMIN_HASH_B64`, `IssueEmail__Password` (required on the host), optional `IssueEmail__UserName` / `FromAddress` / `Host` / `Port` / `Enabled`, `Dashboard__BaseUrl`. Defaults of the mailbox: smtp.hostinger.com:587 (STARTTLS), user and sender `precog@vidasoftservices.com`; sending as another mailbox or sender (for example no-reply@ through an info@ account) is a pure `.env` change, but a Hostinger mailbox may refuse a sender that is not its own or an alias - try it before relying on it.

## The Dashboard (slice S5)

- **Public pages** (no session; routes outside `RequireAuth`, `src/pages/account/`): `/accept-invite`, `/forgot-password`, `/reset-password`, each in a shared card (`AccountPageShell`) with an EN / HU switch. The single-use token is read **once** from the URL fragment (`#token=...&lang=hu`, `src/lib/linkToken.ts`), kept in the page's state only and removed from the address bar at once (`history.replaceState`), so it stays in no history entry or copied address; the `lang` of the link sets the language. `AcceptInvitationPage` first asks `POST /api/Accounts/Invitations/Info` and shows the Company, the role and the e-mail address, then (password rules checked on the page, `src/lib/passwordRules.ts`, and again by the API) creates the account with `.../Invitations/Accept`; `ForgotPasswordPage` posts the address and always shows the same answer; `ResetPasswordPage` confirms the new password and offers a new link when the token is used up or expired. None of these calls carries an HMAC key. The texts the API sends (the password rules, the refusals) are English; the pages show them through `t()`, and every known one has its Hungarian text in `src/lib/translations.accounts.ts`.
- **The sign-in page** has a "Forgot your password?" link; its first field is "Username or e-mail address" (the API accepts the login name or the e-mail).
- **The platform administrator** (`CurrentUserDto.isPlatformAdmin`, `AuthContext.isPlatformAdmin`): `visibleNavEntries` shows it ONE entry, "Companies" (`/platform/companies`, `RequirePlatformAdmin`), and nobody else sees that entry; `AppShell` sends it there from every other path and never shows it the Company-less state. `PlatformCompaniesPage`: the Companies (people / Admin counts, a lock for a WordPress-synchronized one, "No Admin yet"), create a Company, and for the selected one its people with grant / revoke of Admin and Reader (revoking asks first; the API's last-Admin refusal is shown translated), the pending invitations with withdraw, an invite form (e-mail, role, the language of the mail) and enable / disable (not for a locked Company; asks first). It shows names, states, counts and the people who administer a Company - never telemetry, Issues, Devices or models.
- **Not yet in the Dashboard** (slice S4 and the second Dashboard slice): the Company Admin's own invite panel in "Users & Access", the logo upload, the Company switcher, the server registry.
- **Tests**: `AccountPages.test.tsx` (the invitation page with its link language, the token out of the address, the password rules before any request, expiry, the API's refusal in Hungarian, forgot / reset), `PlatformCompaniesPage.test.tsx` (list, create, the refusal for an existing name, people and invitations, invite payload, withdraw, grant, revoke with a confirmation and the last-Admin message in Hungarian, a locked Company cannot be disabled), `RequirePlatformAdmin.test.tsx` and `linkToken.test.ts` / `passwordRules.test.ts`. A real-Chromium pass with a mocked API at 1366 and 390 px: no horizontal overflow, no console errors, nothing reached a real API, and the platform administrator opening `/devices` is sent to `/platform/companies`.


## The Company Admin's people, removal, and where the password is managed (slice S4b-1, 2026-11-24)

- **Origin of every member**: `CompanyMemberDto.origin` ("Local", "WordPress", "EntraId") and `synchronizedFromWordPress` on both member lists (`GET /api/Company/Members`, `GET /api/Platform/Companies/{id}/Members`), so the Dashboard can mark a WordPress User. A person that was removed and kept as a deactivated row is not listed or counted.
- **Removal** (`DELETE /api/Company/Members/{userId}` for the Company Admin, `DELETE /api/Platform/Companies/{companyId}/Members/{userId}` for the platform administrator; `UserRemovalService`): anyone can be removed EXCEPT a User synchronized from WordPress **while the synchronization is on** (409 "...synchronized with WordPress. Unlink it from WordPress first, or switch the synchronization off.") and the Company's **last enabled Admin** (409 "...make someone else an Admin first."); the check and the change run in one transaction under the Company's advisory lock. A User with no history is deleted; one that others' records point to (an Issue it reviewed, a training or Ollama job it requested, a category or knowledge share it created or approved - RESTRICT foreign keys, on purpose) is **deactivated** (`deactivated: true`): disabled, roles / grants / identities / tokens / password / login name / e-mail removed (the address can be invited again), only the display name stays on the old records. Cached access keys of the person are dropped at once.
- **Where the person manages the password** (`WordPressLinkService`; `POST` / `DELETE /api/Company/Members/{userId}/WordPressLink` and the same under `/api/Platform/Companies/{companyId}/Members/{userId}/WordPressLink`): **Unlink** makes a WordPress User a locally managed one (origin Local, not locked, the WordPress identity removed; it keeps the hash copied last, so it still signs in, and then changes the password here by a reset e-mail; the synchronization no longer touches it). **Link** (only while the synchronization is on) connects a locally managed User to the ONE approved WordPress account with the same e-mail address (404 none, 409 ambiguous or already linked to another User): WordPress becomes the authority, the copied hash replaces the one set here (the old password stops working), the profile is copied and the User is locked.
- **Roles are managed here for every User**, also one synchronized from WordPress (WordPress provides no role): the platform administrator's grant / revoke no longer refuses a locked User.
- **The Company Admin invites** (`GET` / `POST /api/Company/Invitations`, `DELETE /api/Company/Invitations/{id}`): one person at a time, by e-mail, as Admin or Reader, with the same flow and rules as the platform administrator's invitation (`AccountFlows`).
- **The platform account** also signs in with its well-known name **"VSSSysAdmin"** (same password as with the e-mail; the access token is always built from the e-mail). Its e-mail alone identifies it for invitations. The WordPress mirror's hash of that account and the `.env` hash are the same value (checked 2026-11-24, equal), so both sign in with the same password.
- Tests: `MemberManagementTests` (removal of a Reader, a WordPress User while the sync is on / off, the last Admin, a User with a history deactivated and its address free again, access keys dropped, only a Company Admin may use the endpoints; unlink and link with every refusal; the origin on the list; one-by-one invitations), `PlatformAndInvitationFlowTests`, `AccountManagementTests`.


## The Dashboard: the people of a Company (slice S4b-2)

- **Users & Access** (the Company Admin, `ReadersPage` "Company members"): every person shows where they come from - a **WordPress badge** (icon and text, `WordPressBadge`) for a User synchronized from WordPress - and has the roles checkboxes (a WordPress person's roles are managed here too, WordPress provides none), a **Remove** button and **Link to WordPress** (a locally managed person) or **Unlink from WordPress** (a WordPress person). Each of them asks first (`MemberActions`, `ConfirmDialog`): removal says the person can no longer sign in or reach the Company; unlink says the password is managed here from now on (the one copied last keeps working until changed); link says WordPress becomes the place of the password and the password set here stops working. The API's refusals are shown with their own texts, translated: a person synchronized from WordPress cannot be removed while the sync is on, the last Admin cannot be removed, link refusals (sync off, no / several / already linked WordPress account). A person with a history is deactivated instead of deleted and the toast says that the history stays.
- **Invitations** (`InvitePanel`, shared with the platform administrator's Company page): the Company Admin invites one person at a time by e-mail as Admin or Reader (Reader by default; the platform page defaults to Admin), in English or Hungarian, sees the pending invitations and withdraws one. The link exists only in the e-mail.
- **The platform administrator's Company page** uses the same components: the WordPress badge, Remove / Link / Unlink for every person and the shared invitation panel.
- The "Role is synchronized from WordPress for this Company" notice and the Company profile badge are gone: roles and Companies are PRECOG's.
- Tests: `MemberActions.test.tsx` (the right link action per origin, nothing before the confirmation, removal and the deactivated message, the refusal in Hungarian, unlink / link), `ReadersPage.test.tsx` (one badge for the WordPress person, roles editable for them, removal after the confirmation, the last-Admin message in Hungarian, unlink, one-by-one invitation with the Reader default, withdraw), `PlatformCompaniesPage.test.tsx`.
