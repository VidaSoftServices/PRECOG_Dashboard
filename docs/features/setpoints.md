# Setpoints (target / tolerance intervals)

The Device page's setpoint tools: "Export all sensors" (with each Sensor's current setpoint), "Manage Setpoints" (export every interval, import a sheet as the complete truth for the Sensors it mentions, preview and sequential apply), and "Delete setpoints..." on the Policies page. The setpoint columns of the Sensor import are in `sensor-import.md`.

Related: the API side of this feature is in [../../../PRECOG_API/docs/features/setpoints.md](../../../PRECOG_API/docs/features/setpoints.md).

The text below was moved verbatim from `CLAUDE.md` (Dashboard) on 2026-11-19; dates and "superseded" notes are the original ones. Keep this file up to date with every change to the feature.

## Device page: Export sensor for hardware, Export all sensors, Manage Setpoints, deleting setpoints

The Sensors header of the Device page (Admin only) now reads, left to right: **Add Sensor**, **Import Sensors** with **Export all sensors** directly under it, **Manage Setpoints**, **Export sensor for hardware**, **Analyze**.

- **Export sensor for hardware** is the button that used to be called "Export sensor_map" (same file, same behaviour: the firmware's `sensor_map.h` text as `sensor_map-device-{id}.txt`).
- **Export all sensors** (`ExportAllSensorsButton`, `src/lib/sensorExport.ts`) downloads `sensors-device-{id}.csv`: one row per Sensor with exactly the template's columns - `sensorName, displayName, direction, sensorType, unitCode, rawScale, rawLookback, rawMinIssueScore, Calculate` and the six setpoint columns `target (optional), tolerance (optional), targetAbove (optional), targetBelow (optional), toleranceAbove (optional), toleranceBelow (optional)` - so it can be edited and imported back; importing it unchanged changes nothing (tested end to end: the import sends no write, setpoints included). The setpoint columns hold the Sensor's **current** setpoint: the interval **in effect now** (started, not ended; the one that started last if several), in the columns of the Sensor's direction (`target`/`tolerance`, or the four above/below columns for a bidirectional Sensor); a Sensor with none in effect - no interval, only ended ones, or only a future one - gets empty cells, because exporting a past or future interval as "current" would make a re-import create an interval that does not exist today. The full history of every interval is the **Manage Setpoints** export. The raw policy values and the setpoints come from **two** Device-wide reads (the new read-only `GET /api/Devices/{deviceId}/AggregationPolicies` and `GET /api/Devices/{deviceId}/Setpoints`), made fresh when the button is pressed.
- **Manage Setpoints** (`ManageSetpointsDialog`, rules in `src/lib/setpointSheet.ts`, requests in `hooks/setpointSync.ts`): **Export all setpoints** downloads `setpoints-device-{id}.csv` (header `sensorName, validFrom, validTo, target, tolerance, targetAbove, targetBelow, toleranceAbove, toleranceBelow`; one row per interval, UTC ISO dates, empty validTo = open-ended; a Sensor with no interval gets a bare row so it can be filled in) from the new `GET /api/Devices/{deviceId}/Setpoints` (one request). The sheet can be pasted or chosen as a file and is imported as **the complete truth for the Sensors it mentions**: for every Sensor that appears, a stored interval with no row any more is **deleted**, a row with no stored interval is **created**, a row with the same validFrom but different values or validTo **replaces** it (deleted and created again; an interval is identified by its validFrom); a Sensor that keeps only its name (an empty row) **loses all its setpoints**; a Sensor that does **not appear at all is not touched**. A single row without validFrom starts at the moment of the import. Everything is validated before the first request (unknown Sensor, bad date/number, target/tolerance on the wrong side for the Sensor's direction, validTo before validFrom, duplicate validFrom, overlapping intervals, a sheet without the validFrom / setpoint columns - which would otherwise delete everything it lists) and **previewed** ("What will be done" lists every DELETE / CREATE); if anything will be deleted an explicit confirmation checkbox enables Apply. Applying is sequential (per Sensor all deletes, then the creates in chronological order; a failed delete skips that Sensor's creates; 429 waits Retry-After; 401/403 or Stop ends the run) and not atomic - importing the same sheet again finishes whatever did not go through, because the plan is recomputed from what is stored.
- **Delete setpoints...** (`DeleteSetpointsDialog`) is a button at the end of the Setpoints card on a Sensor's Policies page (Admin only, shown when there is something to delete): pick intervals (or Select all), confirm, and each is removed with the new `DELETE /api/Devices/{deviceId}/Sensors/{sensorId}/Setpoints/{setpointId}`. Neighbouring intervals keep their own validity (a gap can remain; a measurement with no effective setpoint is not analysed), already found Issues are not changed, no retraining is scheduled. The Setpoints card text no longer says "append-only, never edited or deleted".
- **Fixed on the way:** the raw/base policy was recognised by the lower-case names "native" / "raw", but the API sends the names as stored ("Native" / "Raw"); the check is now case-insensitive (`isRawPolicy`, `src/lib/policies.ts`), so the Policies page really shows the raw policy's retraining notice and the Sensor import can find a Sensor's raw policy to update. The bulk-operation retry helper (429 Retry-After, 401/403 stop) moved to `src/api/rateLimited.ts` and is shared by the Sensor import and the setpoint sync. `schema.generated.ts` was regenerated from the API's OpenAPI document for the three new operations.
