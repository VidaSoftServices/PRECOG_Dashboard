## Two languages: English and Hungarian (2026-11-19)

- **Rule from now on: every user-visible text is written in both languages.** The English text is the key: `t('Overview')` (`useT()`, `src/lib/language.ts`) returns the Hungarian from `src/lib/translations*.ts` when the language is Hungarian and the English text itself when there is no translation (or in English). Placeholders are positional: `t('Delete {0} setpoint(s)', n)`; the Hungarian text may put them in a different order. Outside React use `tr(...)` / `translate(...)`. `src/lib/translations.test.ts` fails when a `t('...')` in the code has no Hungarian text.

- **Switch**: the language icon (`EN`/`HU`) in the top bar, left of the theme menu (`LanguageMenu` in `AppShell.tsx`). The choice is a harmless UI default kept in `localStorage` (`precog.language`), like the theme; nothing auth related.
- **Files**: `translations.ts` (shell, merges the others), `.admin` (Company settings, Logs, Users & Access, Smart Analytics), `.devices`, `.misc` (Issues, Knowledge Sharing, Monitoring, Overview, Training, Ollama, Status, Login, states), `.fragments` (a sentence with a number/name/code inside is translated in ordered pieces), `.dynamic` (texts with placeholders, toasts, state-dependent button labels), `.status` (pills, shared dialogs, chart labels). The toast layer translates its title and body centrally (`ToastProvider`), so a toast text needs a Hungarian entry but no call-site change.
- **How the existing pages were converted**: a one-off script (TypeScript AST) wrapped the JSX texts, the label/title/description/placeholder/... attributes, the strings in conditionals/template literals of those, and the `toast.*` arguments in `t()`; sentences that mixed English words into JavaScript (singular/plural) were rewritten by hand into whole-sentence keys. **Not translated**: the validation/error messages produced in `src/lib` (CSV import problems and the like), text that comes from the API (error bodies), and the column names of the sheets.

> The "Descriptions" bullet of this section is in `descriptions.md`.

- **Issue text, both ways**: the API keeps `message` (written in Hungarian or English) and, made by Ollama about five minutes after the Issue's last change, `messageHu` and `messageEn` (the model works out the language and translates into the other one; see the API's CLAUDE.md). `localizedIssueMessage` (`src/lib/issueMessage.ts`) picks the one of the chosen language and falls back to `message` until it exists. The Admin edits the text **in the language that is shown** (the feedback box starts with the text of the chosen language); saving sends it as the new `message` (`PUT` with only `message`), the API clears both translations and, five minutes after the last change, translates it into the other language. Below the box an Admin sees the OTHER language read-only ("translated automatically", or "not translated yet"). **The last edit wins**: if both languages are edited one after the other, the later save becomes the `message` and the other language is made again from it (what was written there is replaced); the editor shows a warning to that effect as soon as the text is changed. An edit can be made in either language - the model works out which one it was written in. `messageHu`/`messageEn` are typed in `issueMessage.ts` until `npm run gen:api` is run against an API that has them.
