# PRECOG Dashboard — Agent Instructions

Permanent rules for anyone (human or agent) working in this repository.
For product/domain/architecture explanation, see `CLAUDE.md`. For live
progress, phase status, and matrices, see `TASK_IMPLEMENTATION.md`. This
file states rules only — it does not track status.

## Repository boundary

- `C:\VS\PRECOG_Dashboard` is the only editable repository.
- `C:\VS\API` (the VidaSoft.API/DataAccess/MLTraining solution) is read-only
  reference material — for understanding the contract and its intent, never
  for editing.
- Backend contracts must never be changed for frontend convenience. If a
  workflow needs something the API doesn't provide, document the gap (see
  `CLAUDE.md`'s "Missing backend capabilities" section and
  `TASK_IMPLEMENTATION.md`'s missing-capability log) — do not fabricate
  frontend behavior to paper over it.
- Do not modify database configuration, migrations, connection strings,
  Docker networking, hosts files, launch settings, `MLTraining`, or
  `PredictionCalc.dll` — none of that lives in this repository and none of
  it is this project's concern.

## Source-of-truth precedence

When sources disagree, resolve in this order:

1. The latest explicit user instruction in the current conversation.
2. The live generated OpenAPI contract (`http://localhost:5065/swagger/v1/swagger.json`,
   regenerate via `npm run gen:api`) for exact routes, methods, parameters,
   request/response DTOs, operation IDs, security requirements, and status
   codes.
3. This file (`AGENTS.md`).
4. `CLAUDE.md`.
5. `TASK_IMPLEMENTATION.md`.
6. Backend `VidaSoft.API/AGENTS.md` and `VidaSoft.API/CLAUDE.md` for domain
   invariants (business rules, not wire format).
7. Backend `VidaSoft.API/TASK_IMPLEMENTATION.md` for business intent behind
   API operations.
8. Backend `DataAccess/Solution_Description/API_Integration_Guide.md`.
9. Backend `DataAccess/Solution_Description/Database_Redesign_Change_Description.txt`.
10. The old dashboard (deleted from this repo's active tree, still visible
    in Git history) and that Git history — product/workflow reference only,
    never a technical or architectural source of truth.

**This dashboard's documentation must never redefine backend behavior.** If
the live OpenAPI contract and a backend doc disagree, the live contract wins
for wire format; the doc's *business intent* still applies to how the
frontend presents that data. Record the disagreement — don't silently pick
one and move on. See "Handling backend doc/contract disagreement" below.

## Approved frontend stack

- React 19, Vite 6.
- Strict TypeScript (see "Permanent implementation rules" below for exactly
  what "strict" means here).
- Fluent UI React v9 — `@fluentui/react-components`, `@fluentui/react-icons`.
- React Router 7, with route-level `lazy()` loading for every non-root route.
- TanStack Query for all server state.
- `openapi-typescript` + `openapi-fetch` for the typed API layer.
- Chart.js + `react-chartjs-2`.
- `react-datepicker`, wrapped in exactly one typed, Fluent-integrated
  component (`src/components/DateTimeField.tsx`) — never used raw at a call
  site.
- Light, dark, and system themes via Fluent's `createLightTheme`/
  `createDarkTheme` and a `prefers-color-scheme` listener.

**Do not introduce another** UI component library, router, HTTP transport,
server-state library, chart library, or global state library **unless a
concrete missing capability is documented first** (in `CLAUDE.md`'s gap
section and `TASK_IMPLEMENTATION.md`'s missing-capability log) — not
"this would be nicer," an actual capability the approved stack cannot
provide.

## Permanent implementation rules

- This is a complete TypeScript rewrite. The old dashboard (React 19 + plain
  JSX, no router usage, no API client, hardcoded production URL) is a
  product/workflow reference only — never the technical or architectural
  foundation for anything new.
- Final active application code contains no JavaScript or JSX. `src/` is
  100% `.ts`/`.tsx`.
- Final TypeScript configuration does not use `allowJs`.
- `src/api/schema.generated.ts` is generated by `npm run gen:api` and is
  never hand-edited. If the live contract changes in a way the generated
  file doesn't represent correctly, fix it with a type-only wrapper (see
  `src/api/authHeaderPatch.ts` for the existing precedent) or a
  hand-authored supplement (see `src/api/domainTypes.ts`) — never by editing
  the generated file.
- Pages and components never contain a raw `fetch` or a direct HTTP
  transport call. All API access goes through `src/api/client.ts`
  (`apiClient`) via a typed hook in `src/api/hooks/*`.
- Authentication and session handling are centralized in `src/auth/` — no
  component reads or writes a token itself.
- Routes are role-aware (`RequireAdmin`) and Device-access-aware. Client-side
  route guarding is a UX convenience, **not** a security boundary — the
  backend's own 401/403/404 responses remain authoritative, and guards must
  never be relied on as the only enforcement of anything.
- No hardcoded API URL anywhere in `src/`. The base URL comes from
  `VITE_API_BASE_URL` (`.env.local`, gitignored; `.env.example` documents
  the key with no real value) — `src/api/client.ts` throws at startup if
  it's unset, rather than silently falling back to a default host.
- No fabricated production data. An empty/missing/gapped API response is
  rendered as an empty or gapped state, never invented rows (see, e.g., the
  Training page's explicit "no ModelVersion history" message instead of
  fake "previous version" rows).
- No browser recreation of backend ML, `GetElbow`, Issue qualification,
  canonical grouping, category-suggestion, or knowledge-sharing
  compatibility logic. Every one of those values is rendered directly from
  an API response; the frontend may only compute presentation-only values
  (visible chart range, local sort order, formatting, cursor position) and
  must label them as such where confusion is plausible.
- No raw HTML rendering of API-sourced, User-sourced, category, technician,
  or Ollama text. Render as text content, never via `dangerouslySetInnerHTML`
  or equivalent.
- Every workflow that can fail or be empty implements the states that apply
  to it: loading, empty, stale, validation, unauthorized (403 —
  `NotAuthorizedState`), forbidden/not-found-for-Reader (404, same
  treatment, matching the backend's own existence-hiding pattern),
  conflict (409), rate-limited (429, with the `Retry-After` countdown), and
  network-error. Not every workflow needs every state — a read-only list has
  no "conflict" state — but skipping a state that *does* apply is a defect.
- Any polling page must stay measurably under the API's actual rate limit
  for the endpoint it polls, with a genuine safety margin left for other
  pages and other browser tabs sharing the same client IP — never derive a
  polling budget from database/connection-pool capacity, which is
  architecturally independent of the API's HTTP rate limiter and is never a
  justification for firing more requests (see CLAUDE.md's "Live Monitoring"
  section for the confirmed numbers and the incident this rule comes from).
  A page-level polling orchestrator, not N independent per-item intervals,
  is the default shape once "one item" would mean "N simultaneous
  requests." When such an orchestrator drives its own imperative
  `queryClient.fetchQuery(...)` call specifically to control retry/backoff
  or fetch timing itself, it must explicitly override the query client's
  global `retry`/`staleTime` defaults at that call site (with a comment
  saying why) rather than silently inheriting them — those global defaults
  are tuned for ordinary one-shot queries and will otherwise fight the
  orchestrator's own logic (an uncoordinated internal retry racing a shared
  cooldown; a stale-cache hit silently skipping a fetch the orchestrator
  believed it was making).
- Accessibility and responsive behavior are mandatory, not a follow-up pass
  bolted on later: every new page must use Fluent's accessible primitives
  and be checked against desktop/tablet/mobile at the point it's built.
- No native `window.prompt`/`window.confirm`/`window.alert` anywhere in
  this codebase — they give no styling, focus management, or keyboard
  control, and are inconsistent with an otherwise-Fluent application. Use
  `src/components/ConfirmDialog.tsx` for a consequential-action
  confirmation, or a proper Fluent `Dialog`/`Field`-based form for anything
  that needs real input (see `src/components/MoveToCanonicalDialog.tsx` for
  the reference pattern — a bounded, searchable picker, not a raw prompt).
- Event feedback (a mutation succeeded/failed, a job reached a terminal
  status) goes through the centralized toast layer
  (`src/components/ToastProvider.tsx`'s `useAppToast()`), never a new
  ad-hoc notification mechanism. A toast never duplicates a field-level
  validation error (that stays inline via `ErrorState`/`Field`) and never
  contains a token, Device Secret, credential, raw response body, or
  unfiltered Ollama output.
- Lint, type-check, tests, production build, and runtime verification
  (actually starting the dev server and looking at the result) are mandatory
  before any phase is marked complete — see `TASK_IMPLEMENTATION.md`'s
  verification matrix for current status.
- Old and new active implementations of one route must never coexist at
  completion. A route is either the old dead file (delete it once its
  replacement is verified) or the new one — never both, even temporarily
  past a "this route is done" checkpoint.
- Exactly three dashboard-specific Markdown files exist in this repository:
  this one, `CLAUDE.md`, and `TASK_IMPLEMENTATION.md`. Do not create
  `DASHBOARD_ARCHITECTURE.md`, `API_INTEGRATION.md`, `DECISIONS.md`,
  `PROGRESS.md`, `ROADMAP.md`, `AUDIT.md`, or any other implementation
  document — consolidate into one of the three. An existing `README.md` is
  not affected by this rule.

## Security rules

- The custom HMAC authentication scheme (`HMAC_Key` header, never
  `Authorization`/Bearer/cookies) must be respected exactly as the live API
  implements it — this dashboard never invents a second auth scheme.
- The only human roles are Admin and Reader. `DevicePrincipal` is a machine
  identity and is **not** an interactive dashboard role — do not build a
  DevicePrincipal login UI; `Request_Device_Token` exists for machines, not
  humans, per backend `AGENTS.md`'s "Device authentication and migration
  ownership."
- Tokens and Device Secrets must never appear in a URL, a log statement,
  analytics, exported/persisted state, or a committed environment file. The
  human session token lives only in `src/auth/authStore.ts`'s in-memory
  closure — never localStorage/sessionStorage/a cookie.
- The raw DevicePrincipal Secret is shown exactly once, immediately after
  `Provision`/`Rotate`, in a dialog's local component state only — never
  written to React Query cache, browser storage, or a URL. See
  `src/pages/devices/DevicePrincipalPage.tsx` for the reference
  implementation.
- Backend-, User-, category-, technician-, and Ollama-authored text is
  always rendered as text (see the raw-HTML rule above).
- Examples, tests, and fixtures use placeholder credentials only — never a
  real username, password, token, or Secret, even one that's expired or
  fake-looking-but-real-shaped.

## Final telemetry contract

- `SignalInputData`, `CurveInputData`, `BiSignalInputData`, and
  `BiCurveInputData` each carry their own required `sensorId` on every array
  item.
- The four ingestion endpoints have **no** competing query-level `sensorId`
  parameter — this was revoked by the backend and must never be
  reintroduced or assumed by this frontend.
- One ingestion batch may reference multiple Sensors only when they all
  belong to one authorized Device.
- Backend validation of ownership, batch limits, and per-item correctness is
  authoritative — the frontend does not need to (and should not try to)
  duplicate it, only surface the resulting error clearly.
- This dashboard does not currently build a telemetry-ingestion UI — that's
  a DevicePrincipal (machine) concern, out of scope for a human-facing
  dashboard, per the DevicePrincipal-is-not-an-interactive-role rule above.

## Handling backend doc/contract disagreement

When a backend documentation file and the live OpenAPI contract disagree
(this has already happened twice — see `CLAUDE.md`'s discrepancy list):

1. Do not modify the backend.
2. Follow the live OpenAPI contract for exact request/response integration.
3. Follow the backend docs' stated business intent for frontend *behavior*
   (when to poll, what a status transition means, who's allowed to do what).
4. Record the discrepancy in `TASK_IMPLEMENTATION.md`'s source-reading log.
5. Continue all frontend work that isn't blocked by the discrepancy.
6. Never invent missing data or behavior to paper over it.
